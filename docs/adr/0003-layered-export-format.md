# ADR 0003 — Layered export format and PSD/PSB limits

- **Status:** Accepted
- **Date:** 2026-11-05
- **Deciders:** PrintSheet engineering
- **Evidence:** [`docs/spikes/psd-spike/`](../spikes/psd-spike/README.md)

## Context

The sheet is exactly 58 cm wide, i.e. 6850 px at 300 DPI. Height is minimized
and can reach roughly 500 cm, i.e. about 59,000 px. The shop needs:

- a print-ready flat file at 300 DPI with correct transparency;
- a placements manifest so the sheet can be audited or rebuilt;
- ideally a layered document the operator can open in Photoshop to nudge or
  inspect individual designs.

The classic Photoshop PSD format limits each side to 30,000 px (about 254 cm at
300 DPI). PSB is the large-document variant. The export pipeline is Python and
the development machine has no Photoshop.

A spike measured `psd-tools` 1.26.0 / Pillow 13.0.0 on Python 3.14.8 with
ImageMagick 7.1.2-34. Full method and raw results:
[`docs/spikes/psd-spike/README.md`](../spikes/psd-spike/README.md).

Measured facts:

| Case | Result |
| --- | --- |
| 30,000 × 64 | Classic PSD (version 1); byte-identical layer round-trip |
| 30,001 × 64 | Automatically promoted to PSB (version 2); layer record correct |
| 64 × 30,001, layer at y=30,000 | PSB; offset preserved |
| 6850 × 5900, 4 layers | Classic PSD; byte-identical layer round-trips; 122.7 MB; 0.56 s; 231 MB traced peak |
| 6850 × 31,000, 1 layer | PSB; 637 MB; 0.63 s; 1215 MB traced peak |

Critical limitations:

1. `psd-tools` enforces the **PSD** 30,000 px limit when compositing or reading
   layer rasters, even for PSB. Opening the PSB structure and reading layer
   names/bboxes works; reading pixels above the limit fails with
   `ValueError: Image ... exceeds the PSD maximum of 30000 px per axis`.
2. Writing a PSB above the limit requires setting the private
   `doc._updated = False` before `save()`. This skips the preview rebuild and
   leaves a stale/initial composite. It is a spike workaround, not a supported
   production path.
3. The writer is not strip-based. A 6850 × 31,000 save peaks at ~1.2 GB of
   traced Python memory; extrapolating linearly to 6850 × 59,000 gives ~2.3 GB,
   before native buffers. One tall sheet is an OOM risk.
4. `PSDImage.new()` defaults to RAW canvas compression, producing a 637 MB file
   for a mostly empty tall canvas. File size is a delivery problem.
5. Embedding 300 DPI works only through a raw `ImageResource` for
   ResolutionInfo; the library’s `ResoulutionInfo` writer has a signature bug
   in 1.26.0.

## Decision

Guarantee a **layered-equivalent bundle** instead of a true layered PSB:

1. **Flat transparent PNG or TIFF at 300 DPI**, rendered in horizontal strips
   from the approved full-resolution versions, with correct pHYs/DPI metadata.
2. **JSON placements manifest** containing the sheet geometry, every placement
   (design ID, version ID, source path, cm and px geometry, 90° rotation),
   integrity report ID, and the exact source file hashes.
3. **Photoshop `.jsx` rebuild script** that reads the manifest, opens the
   source files, and recreates one layer per design at the recorded position
   and rotation. The operator can run it in Photoshop to obtain a layered
   document locally, where Photoshop’s own PSB writer handles the size.

Expose this as export format `psd-bundle`.

Additionally:

- `flat-png` and `flat-tiff` are always available within configured limits.
- `layered-psd` is available only when both sheet dimensions are ≤ 30,000 px,
  and only after the layered writer passes pixel-equality tests.
- `layered-psb` is **not** offered until a strip-based writer exists and has
  been smoke-tested in real Photoshop. The API returns
  `export-format-unavailable` (422) rather than emitting a file the shop cannot
  trust.
- The export dialog states the sheet size and which formats are available
  before the operator commits.

The manifest + source files are the source of truth. Any layered artifact is a
derived convenience and must never be the only deliverable.

## Consequences

Positive:

- The guaranteed path is strip-renderable, memory-bounded and works at any
  realistic sheet height.
- The bundle is auditable: manifest + immutable version files reproduce the
  sheet exactly.
- No dependency on private psd-tools state or on Photoshop being installed on
  the server.
- Operators who want layers can still get them, generated by Photoshop itself.

Negative:

- `psd-bundle` requires a manual `.jsx` run for a true layered document.
- The manifest and source files must be retained; deleting versions breaks
  rebuilds. This aligns with the “nothing is lost” rule.
- A future true-PSB writer remains work, not a solved problem.
- TIFF/PNG strip rendering and DPI metadata still need implementation and tests
  in Phase 1 C.

## Alternatives considered

- **Use psd-tools PSB as the primary layered export.** Rejected: private-state
  workaround, stale composite, cannot read back above 30,000 px, ~2.3 GB
  extrapolated peak, huge RAW files, no Photoshop validation.
- **Automate Photoshop via COM/ExtendScript on the server.** No Photoshop on
  the machine; Windows-only; fragile; violates the local Linux deployment.
- **ImageMagick to assemble a layered TIFF/PSD.** ImageMagick can read the PSB
  but does not solve layer authoring, memory or validation; TIFF layers are not
  a Photoshop-native workflow.
- **Flat file only.** Loses the operator’s ability to inspect/adjust individual
  designs and weakens auditability.
- **Custom PSB writer now.** Correct long-term, but too large for Phase 0 and
  still needs Photoshop smoke tests. Keep it as future work behind the same
  API format gate.
